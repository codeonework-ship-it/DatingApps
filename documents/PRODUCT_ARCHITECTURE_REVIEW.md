# Connect — Product and Software Architecture Review

Review date: 2026-09-26 · Scope: repository requirements, architecture and delivery evidence, with selected code checks.  
Companions: [Master FRD](CONSOLIDATED_FRD.md), [traceability](REQUIREMENTS_TRACEABILITY.md), [source register](DOCUMENT_SOURCE_REGISTER.md).

## 1. Assessment

The repository describes a broad dating product with a substantially implemented local native-PostgreSQL foundation. The strongest documented capabilities are credential signup, resumable profiles, mutual matching, activity-based unlock, durable chat/replay, safety enforcement, operator controls and bounded retry behavior. The most urgent product task is to establish a trustworthy release boundary and resolve conflicting policies, rather than treat every old backlog as unfinished or every completion report as launch approval.

The architecture has useful correctness mechanisms: durable workflows, transactional outboxes, immutable audit/XP ledgers, scoped operators, shared idempotency and recoverable media cleanup. The remaining risk concentrates at boundaries: public versus private profile data, identity/consent policy, money versus local ledger records, call metadata versus actual media, accepted events versus device delivery, and local tests versus deployed operations.

This review supplies a working baseline, not a fresh security audit or test certification. “Documented implemented” means a source report says so. A code observation below is a static spot-check, not a verified exploit or full feature assessment.

## 2. Product recommendations

1. Make safe, meaningful matched conversations the core outcome. Treat raw session volume, gift spending and XP accumulation as supporting metrics; do not optimize them at the expense of consent or report rates.
2. Define launch market, audience, supported platforms and the role policy for every supported pairing. Existing gender options and women-led unlock language are insufficient to define same-gender/nonbinary behavior.
3. Freeze the current signup journey and use the durable workflow as authority. Retire OTP and the removed basic-info screen from new work; preserve their historical documentation for traceability.
4. Distinguish “profile complete”, “media approved”, “identity verified” and “eligible for discovery/chat”. A single completion percentage cannot encode all four states.
5. Release optional integrations independently. Do not market live calls or settled payments based on local session/subscription records. Scope can defer those features while preserving the complete core flow.
6. Define a single set of economics: currency, tiers, entitlement windows, price changes, free gifts, exclusive limits, grants, refunds and reward limits. XP and wallet coins are separate economies.
7. Keep production verification, moderation, push and operational gates visible. Existing credentials/provider code do not replace acceptance on real traffic/devices or staffing.

## 4. Architectural risks and actions

| Risk | Evidence and implication | Recommended action / proof |
|---|---|---|
| Shared write ownership | Native runtime diagram shows BFF repositories and services accessing PostgreSQL. A microservice label does not enforce aggregate ownership. | Document command owner and transaction boundary for each aggregate; test invariant enforcement through every route. Avoid a wholesale rewrite while local flows work. |
| Public/private profile coupling | Profile-details provider still attempts `/profile/{id}/draft`; new auth protects self-owned data. | Public projection should carry only approved fields/photos. Test detail completeness without draft read permission. |
| Idempotency lease ambiguity | Shared replay layer documents that owner work may exceed its lease and provider calls need independent dedupe. | Enforce domain command uniqueness, wallet/reward invariants and provider keys. Test crash before/after commit and lease takeover; do not advertise universal exactly-once processing. |
| XP side-effect loss | Current progression doc says failed XP side effect is logged for repair while the domain activity succeeds. | Define durable source-event dispatch/reconciliation and replay IDs. Prove repair after process death with one ledger entry, without reversing the valid activity. |
| Stream revocation | Next-request token denial is documented; stream creation and reconnect are tested separately. | Establish policy and prove denial/termination for an already-connected socket after ban, block, unmatch and token expiry. This review did not establish a vulnerability. |
| Expired replay cursors | Outbox retention removes old rows; replay only promises non-expired events. | Define stale-cursor signal and full-state recovery; test a client offline longer than retention. |
| File/database dual writes | PostgreSQL cannot atomically commit an external object write/delete. Recoverable local lifecycle is documented. | Preserve explicit stage/commit/delete-pending states and retries; verify private S3 and backup restore follow equivalent rules. |
| Feature flags | Current console polls at 15 seconds; at least nudge disablement is server-enforced. | List per-flag presentation and command enforcement. Test stale client and direct API calls, especially billing/calls/SOS; hiding UI alone is insufficient. |
| Multiplying DB pools | Default pool size is per process, with additional transactional pools and workers. | Calculate total connections across replica counts and reserve operational headroom. Verify load shedding before raising pool limits. |
| Notification success semantics | Empty-window queue metrics can look healthy, and provider acknowledgement is not OS display. | Separate intent/inbox/provider/device/tap outcomes. Use traffic-required gate and twelve physical-device cases. |
| Money correctness | Audit says provider settlement, refunds/reconciliation and accounting remain incomplete despite durable local records. | Use ledger and settlement specifications before real-money enablement; test double spends, reversal and out-of-order webhooks. |
| Operational assumptions | Old VPS runbooks describe Supabase and IP-only HTTP/OTP smoke calls. | Produce a deployment-specific native-runtime runbook, transport/secrets plan, restore proof and operator access controls before reuse. |

## 7. Documentation maintenance

Use the consolidated FRD for cross-domain behavior, the current architecture documents for implementation boundaries, and OpenAPI for exact payloads. Keep original BRDs and reports as provenance. Archive status in the source register is an authority classification, not file deletion.

Do not copy old “100% complete”, developer credentials, schema counts, sprint estimates, or pricing assumptions into the new baseline. Review supporting QA documents by section: several have modern credential cases alongside stale basic-info, Supabase, or header-auth rows. Historical source dates are not reliable freshness indicators when files were edited later.

Before the next release, update these artifacts with real decision owners, actual accepted changes, and commit-specific evidence. This review intentionally leaves unproven integrations and unsigned approvals visible.
